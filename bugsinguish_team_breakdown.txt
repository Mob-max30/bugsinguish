0. HOW THIS DOCUMENT IS ORGANIZED
--------------------------------------------------------------------------------
This is a task-assignment document, not a pitch doc — the pitch is already
covered in your README/Reacme. This file exists to answer three questions for
every single deliverable in the project:

  (a) WHO owns it
  (b) Is it INDEPENDENT (can start immediately, no blockers) or DEPENDENT
      (needs another person's output first)
  (c) HOW it should be built — specifically, whether it's a task suited to
      heavy AI-agent prompting (Antigravity + Gemini Pro) or a task better
      done as guided step-by-step prompting with a free-tier LLM (Claude/
      ChatGPT web UI, no IDE agent)

WORK DISTRIBUTION PRINCIPLE (as requested):
  - Pranav + Ujwal → own the majority of the AI-orchestration-heavy and
    agentic-coding-heavy modules, since you both have Antigravity IDE with
    Gemini Pro. These are the modules where an agentic coding assistant
    genuinely saves the most time: large scaffolds, multi-file features,
    realtime UI, and non-deterministic AI-pipeline logic.
  - Pavan → owns the modules that are self-contained, well-documented,
    and easy to build via copy-paste prompting in a free ChatGPT/Claude
    chat window (no IDE agent needed) — mostly backend CRUD, schema setup,
    and infra config. These don't need an agentic IDE because they're
    single-file, well-scoped, and each has abundant boilerplate/examples
    online that a plain chat LLM handles fine.

This keeps Pavan's plate lighter in raw prompt-complexity while still giving
him clear, demo-critical ownership (the backend is still the system's spine —
it's just built through simpler prompts).

3.3 PAVAN — Backend Core, Database & API
     Tool: Free-tier ChatGPT/Claude (plain chat prompting, no IDE agent)
     Branch: feature/pavan-api
--------------------------------------------------------------------------------
OWNERSHIP: The backend spine — data model, CRUD endpoints, embeddings/
dedup storage, and the SSE transport layer. Every task here is scoped
tightly enough to build via a normal chat LLM: describe the file, paste
back the code, test it, move to the next file. No multi-file agentic
scaffolding required.

INDEPENDENT (start Day 1, no blockers):
  1. Go server bootstrap — main.go with Chi router, basic health-check
     route, CORS middleware for local frontend dev.
  2. models/ticket.go — the Ticket struct (id, title, description, stack
     trace, repo branch URL, severity, status, embedding vector, diagnosis
     JSON, diff text, created_at, updated_at). POST THIS SCHEMA TO THE
     TEAM CHANNEL FIRST — it's the unblocking artifact for both Pranav and
     Ujwal (see section 2).
  3. db/neon.go — Postgres connection setup + pgvector extension
     enablement + migration for the tickets table.
  4. CRUD endpoints: POST /tickets, GET /tickets, GET /tickets/:id,
     PATCH /tickets/:id (status updates). Standard REST, no AI logic yet —
     just persistence.
  5. Embedding generation call — wrap the Google Gen AI SDK's embedding
     endpoint (this is a single API call, not agentic reasoning — well
     suited to a plain prompt).
  6. pgvector similarity query — "find tickets whose embedding is within
     threshold X of this new embedding," wired into the POST /tickets flow
     to do dedup-check before creating a new ticket.
  7. SSE endpoint (GET /api/stream) — basic Go SSE handler + an in-memory
     pub/sub so other parts of the backend (or Ujwal's sandbox code, once
     wired) can publish progress events that get pushed to connected
     clients. Post the exact event JSON shape to the team channel once
     built (this unblocks Pranav's listener + Ujwal's emitters).
  8. docker-compose.yml for local dev (frontend + backend together).

DEPENDENT:
  9. Wire the endpoint that receives Ujwal's sandbox/RCA output and writes
     it onto the ticket record + publishes an SSE "diagnosed" event
     (needs: Ujwal's CrashReport/RCA JSON shape).
